# 결과 설명자료 — 제주 혼잡·이동 진단 Agent

팀 재주도좋다 · v0.4 · 2026.11

## 1. 문제 정의
- 2026년 제주: 내국인 관광객 감소(9월 −8.1%), 외국인 급증(+18.1%), 특정 관광지 쏠림, 버스 준공영제 효율 논란.
- 도민·공무원이 "어디에 누가 몰리는가", "어느 노선·시간대가 비는가"를 직접 확인하려면 SQL·시각화 전문 인력이 필요.
- 센터의 격자·시간대 단위 원천 유동인구·카드 데이터는 반출 불가(허브 공개본은 읍면동·일 집계) → **반출 가능 데이터만으로** 답할 수 있어야 누구나 어디서나 쓸 수 있다.

## 2. Agent 구조
```
(질문 없이) 첫 화면 자율 탐색 discover() ─┐
질문(+최근 대화) → 플래너(LLM 도구호출 | 규칙 기반) → 분석 도구 15개(집계만) → 반출 게이트 → 해설(LLM | 템플릿) → 숫자 검증 → LLM 자기 점검·후속 질문(선택) → 자동 점검 → UI/리포트
```
- **읍면동 유동인구 결합(`jeju_agent/tools/dong.py`)**: 허브 공개 API 유동인구(읍면동·일)와 와이파이 이용자를 법정동→행정동 변환표로 같은 읍면동·날짜에 결합해 유동인구 순위·표본 비율(‰)·주말 쏠림·상관을 낸다. 데이터가 없으면 규칙 플래너가 와이파이 순위로 대체하고 계획에 표시.
- **플래너**: 시스템 프롬프트(스키마·도구 선택표·답변 형식·원칙) + JSON Schema 도구 15개. 도구를 부르기 전 계획 한 문장을 쓰게 하고 이를 🧭 실행 계획 패널에 노출. 최대 6회 호출, 오류 시 1회 재시도, 429/5xx 재시도, LLM 장애 시 규칙 모드로 폴백(폴백 사실도 계획에 표시).
- **도구(14)**: congestion_rank, place_profile, list_places, place_access, bus_station_rank, bus_route_efficiency, hourly_profile, weather_effect, congestion_forecast(주말 혼잡 예측), monthly_brief(월간 브리핑), **compare_periods(전반/후반·평일/주말·두 기간 비교, 2026-11-07 추가)**, **explore_anomalies(자율 탐색, 2026-11-07 추가)**, run_sql(읽기 전용 집계), describe_data.
- **자율 탐색(`tools/explore.py`, `JejuAgent.discover()`)**: 질문을 기다리지 않고 장소(4-05)·정류소(3-04)·노선(3-02)의 일별 값을 평일/주말 중앙값과 비교해 급증(1.8배↑)·급감(0.55배↓)·최근 7일 추세(1.4배↑/0.7배↓)를 찾고, 점수 = |log₂배율|×(1+log₁₀(평소/20))로 정렬한 뒤 유형·구분이 겹치지 않게 상위 3건을 고른다. 전체 합계가 평소의 절반 미만인 날(제공처 공백)과 일 중앙값 20명 미만·관측 2/3 미만 대상은 제외, 관측값 10명 미만은 "수집 공백 가능성"을 표시하고 우선순위를 ×0.3. 첫 화면에 혼잡 상위 5곳 지도와 함께 카드로 보여 주고, 카드를 누르면 해당 대상의 세부 분석 질문으로 이어진다. "눈에 띄는 게 있어?"류 열린 질문도 같은 도구(규칙 플래너·LLM 도구표 모두 등록).
- **게이트**: 식별자 컬럼 제거, 10 미만 셀 마스킹(센터 반출 정책 기준), 500행 상한, 원본 행 차단. 차트는 PNG로 반출.
- **검증**: LLM 답변 숫자를 근거표와 대조(불일치 시 템플릿 대체), LLM 전송 내용 미리보기 탭, 출처 표기 상시.
- **해설**: 결론 / 근거 / 해석·제안 / 한계 4단. 합성 데이터 사용 시 경고 강제.
- **자동 점검(`insight.py`)**: 데이터 출처(실/합성/기본값 채움)·요청 기간과 적재 범위 차이·마스킹·표본 일수·검증 결과·이름 매핑 실패(좌표 없음)를 코드가 모아 한계에 붙임. **이어서 물어보기**: 결과의 1위 장소·정류소를 넣은 후속 질문 3개 제안. 최근 3턴을 맥락으로 전달해 지시어 해석.
- **LLM 부가 단계(`LLM_EXTRAS`, 2026-11-07 추가)**: 답변 뒤 ① `review` — LLM이 자기 답변을 근거 사실·주의 문구와 대조해 과장·인과 표현·오해 소지를 JSON으로 지적하면 자동 점검에 "LLM 자기 점검"으로 붙임, ② `followups` — 결과를 보고 다음 질문 3개를 제안(규칙 제안은 예비). 호출 1회씩 추가되며 파싱 실패·장애 시 규칙 기반으로 조용히 대체. 사이드바 체크박스로 제어.
- **적재(`data/loader.py` + `config/column_aliases.yaml`)**: 헤더 정확 일치 → 별칭 매칭 → 데이터셋별 기본값 순으로 표준화하고 매핑 이력을 provenance에 남김. CSV/XLSX, 인코딩·구분자·날짜 포맷 자동. 테이블 간 이름 연결은 정확 일치 → 정규화 키(공백·괄호·방향 꼬리표·일련번호 무시) → 유일 포함 관계 순. 실데이터와 기간이 겹치지 않는 합성 데이터는 섞지 않고 비활성 처리. `scripts/check_data.py`로 점검(매핑률·미연결 이름 상위 표시).
- 코드 위치: `jeju_agent/agent.py`, `insight.py`, `tools/`, `gate.py`, `llm.py`, `llm_mock.py`, `planner_rules.py`, `data/loader.py`.

## 3. 주요 기능
| 기능 | 질문 예 | 산출 |
|---|---|---|
| 혼잡 순위 | 주말에 가장 붐비는 관광지는? | 혼잡지수·관광/외국인 비중 순위, 지도 |
| 장소 프로필 | 성산일출봉은 언제 붐비나? | 일별·요일·월별, 구성비, 추세 |
| 관광지 접근 | 성산일출봉 가는 정류소는? | 반경 1.5km 정류소 승차·피크 |
| 노선 효율 | 효율 낮은 노선은? / 251번 시간대 | 승객/km/일, 저이용 시간대 |
| 교통약자 정류소 | 어르신이 많이 타는 정류소는? | 경로·장애 비중 순위, 시간대 |
| 강우 영향 | 비 오면 어디가 한산해지나? | 강우일/비강우일 변화율 |
| 주말 혼잡 예측 | 이번 주말 어디가 붐빌까? | 같은 요일 패턴×추세, 구간 제시 |
| 월간 브리핑 | 5월 월간 브리핑 | 혼잡·외국인·노선·강우 한 장 |
| 기간·요일 비교 | 9월 전반과 후반에 어디가 늘고 줄었어? / 평일과 주말 차이가 큰 정류소는? | 대상별 두 구간 일평균·변화율, 증가·감소 상위 |
| 자유 집계 | 월정리 월별 이용자 | LLM 작성 집계 SQL |
| **자율 탐색(오늘의 발견)** | (첫 화면, 질문 없음) / 눈에 띄는 게 있어? / 노선 중에 특이한 점은? | 급증·급감·최근 추세 상위 n건(대상·날짜·관측값·평소·배율·설명), 지도, 세부 분석 질문 |

## 4. 실행 결과 (제주데이터허브 공개 API 실데이터 2025-09, `examples/questions.txt` 16문항)
`python -m jeju_agent.cli --offline --batch examples/questions.txt` → `outputs/samples/batch_offline.json` (계획·자동 점검·후속 질문 포함). 16문항 모두 정상 응답(날씨는 Open-Meteo 2025-09 재분석값, `data/demo/weather_*.csv.gz` 동봉). 대표 결과:
- "주말에 가장 붐비는 관광지는?" → 올레 19코스(주말 혼잡지수 2.03), 지하상가, 쇠소깍 해변 순(정류소·충전소 AP 제외, 관측 20일·일평균 20명 이상).
- "성산일출봉 가는 버스 정류소는?" → 반경 1.5km 정류소 14개, 합산 일평균 승차 518명(가장 가까운 성산일출봉입구 0.26km, 211명).
- "어르신이 많이 타는 정류소는?" → 장애인복지회관 96%, 서귀포향토오일시장 78%, 제주절물자연휴양림 77%(교통약자='기타' 요금제 포함).
- "효율이 낮은 버스 노선은?" → 295-4(성산항~서귀포) 0.27명/km/일; 최고는 360-1(부영아파트~제주대) 125명/km/일.
- "주말 승차 급증 정류소" → 렛츠런파크 3.6배, 관음사탐방로입구 2.3배, 한라생태숲 2.0배; 대학교·학교 정류소는 주말 0.
- "251번 노선" → 251 계열 6개 중 승차 최다 251-6: 일평균 171명(평일 191·주말 117).
- "비 오면 어디가 한산해지나?" → 강우일 기준을 1mm→**3mm로 자동 상향**(1mm로는 9월 관측소-일의 79%가 강우일) 후 관측소별 강우 16일/비강우 14일. 평일 감소폭 1위 탐라도서관(−96%, 41→2명), 방일리공원(−49%), 한라산 성판악탐방안내소(−40%); 반대로 제주항국제여객터미널(+83%)·올레 19코스(+122%)는 비 오는 날 평균이 높았다(상관, 요일·행사 미통제).
- "9월 전반과 후반에 어디가 늘고 줄었어?" → 전체 일평균 +2%, 최다 증가 서귀포의료원(31→46, +49%), 최다 감소 제주항국제여객터미널(197→75, −62%).
- "평일과 주말 차이가 큰 정류소는?" → 전체 −23%, 렛츠런파크 +216%(83→262), 제주한라대학교 −76%(476→115).
합성 데이터 단계에서 심어 둔 패턴(성산 주말 급증, 251 낮 공차, 읍면 경로 비중, 해변 강우 민감)은 모두 회수했고, 실데이터에서는 위처럼 현장과 부합하는 결과가 나온다.
차트: `docs/img/congestion.png`(주말 관광지 혼잡), `rain.png`(교통약자 정류소), `route251.png`(노선 효율).

### 4-1. 실데이터가 드러낸 문제와 수정 (2026-11-05)
| 문제 | 수정 |
|---|---|
| 관측 4일짜리 장소가 혼잡지수 31배로 1위 | 관측일(기간의 2/3)·일평균 20명 하한, 기준선 최소 10명 |
| 1,465개 장소 중 2/3가 정류소·충전소 AP | 관광지 질문에서 자동 제외, 장소명으로 카테고리 추론 |
| 와이파이 좌표 없음 | 4-01 장소명(75%) + 장소명 속 정류소ID→3-03(16%) 보완 |
| 3-04 정류소ID(7자리) ≠ 3-03(9자리) | 정류소명으로 매핑(86%) |
| 요금제에 '경로' 없음(일반/청소년/어린이/기타) | '기타'를 교통약자로 간주, 한계에 명시 |
| 시간대 컬럼 없음 | 시간대 질문을 일 단위 도구로 대체, 계획 패널에 사유 표시 |
| 제공처 날짜 공백(노선 9/21·23) | 자동 점검에 표시 |

### 4-2. 고도화 (2026-11-07)
| 항목 | 내용 |
|---|---|
| 날씨 실데이터 | `scripts/fetch_weather.py`: 기상청 기상자료개방포털 ASOS CSV 변환(관측값) / Open-Meteo(키 없음, 재분석; 브라우저 저장 JSON도 `--open-meteo-json`) / 기상청 API허브. 기상청 CSV를 변환 없이 넣어도 별칭으로 읽힘. 관측소 정보가 없으면 내장 제주 4개 지점(184·185·188·189) 사용. **2025-09 Open-Meteo 4개 지점 120행을 `data/demo`에 동봉**해 강우 문항이 바로 동작 |
| 강우 도구 보강 | `weather_effect`: 강우일 기준 자동 선택(강우일 비율 15~60%가 되는 1·3·5·10·20mm), 맑은 날 일평균 20 미만·강우/비강우 3일 미만 대상 제외, 정류소·충전소 AP 제외, 감소·증가 상위 각 10만 표시, 관측소 배정 벡터화(6.5초→0.1초). 월간 브리핑은 집계본에서 NaN 비중 대신 안내 문구, 시간대 없으면 승차 최저 노선으로 대체 |
| 합성 혼입 차단 | 핵심 데이터가 실데이터인데 기간이 겹치지 않는 합성 날씨·4-06이 있으면 적재하지 않고 "없음"으로 표시 → 강우 질문은 수집 방법을 안내하는 답변. 이전에는 2025-03~04 합성 강수량이 9월 실데이터와 섞여 오류를 냈음 |
| 이름 매핑 | 정류소명→3-03 ID: 정확 일치 + 정규화 키(공백·괄호·[동/서/남/북]·일련번호 무시) → 동봉 축약본 기준 **80% → 99%**(정류소명이 빈 8,132행은 같은 원본ID의 이름으로 복원). 와이파이 장소→좌표: 4-01 정규화·유일 포함 + 3-03 정류소ID·정류소명 → **91% → 93%**. 미연결 이름 상위는 check_data·자동 점검에 표시 |
| 기간 비교 도구 | `compare_periods`: 전반/후반, 평일/주말, 임의 두 기간을 장소·정류소·노선별로 비교(변화율 순, 증가·감소 상위 각 n). 규칙 플래너가 "비교·달라졌·늘었·줄었·전반·후반·차이"를 인식 |
| LLM 자기 점검·후속 질문 | `LLM_EXTRAS=review,followups`: 답변-근거 대조 지적을 자동 점검에 추가, 결과 기반 후속 질문을 LLM이 제안. 실패 시 규칙 대체 |
| 자율 탐색 + 첫 화면 | `explore_anomalies` 도구와 `discover()`: 동봉 축약본에서 "365-30번 노선 9/8 평소의 10.7배", "방일리공원 최근 7일 3.7배", "477-1번 9/5 평소의 16%" 같은 발견이 나옴. 첫 화면을 빈 채팅창 대신 혼잡 상위 5곳 지도·발견 카드·시작 질문 6개로 구성(비전문가가 질문을 못 떠올려도 바로 사용) |

## 5. 검증 방법·한계
- pytest 89개 통과(API 키 불필요; 골든 회귀 20개는 동봉 축약본, 나머지는 합성 데이터): 적재·한글/변형 헤더·기본값·XLSX·구분자·날짜 포맷·정보성 테이블 중복 제거, 도구 15종, 게이트 10 기준, 숫자 검증·환각 대체, PNG, SQL 차단, 오프라인 Agent·지시어 해석, 이름 정규화 매핑, 기상청 CSV 변환·직접 적재·합성 혼입 차단·실기간 강우 효과, 기간 비교 도구·규칙 라우팅, LLM 자기 점검·후속 질문과 실패 대체, Ollama 요청 형식·tools 미지원 안내, 자율 탐색(주입한 급증·급감 검출·열린 질문 라우팅·첫 화면 discover·LLM 숫자 검증 폴백), 골든 회귀(18문항 지문 일치), 그리고 시나리오 LLM(`llm_mock.py`)으로 도구 호출 루프·오류 재시도·호출 한도·장애 폴백·대화 맥락·Anthropic 메시지 변환.
- **LLM 실키 검증(2026-11-07, Anthropic claude-sonnet-5, `LLM_EXTRAS=followups,review`)**: `scripts/llm_smoke.py` 16문항 → `docs/LLM_EVAL.md`·`outputs/samples/batch_llm.json`. 16문항 모두 LLM 경로로 완료(폴백 0), 4단 형식 15/16(데이터 현황 질문만 '한 줄 결론' 제목 생략), 도구 선택은 오프라인 규칙과 일치하거나 더 적절(예: '한라병원 정류소 몇 시' → 시간대 도구 시도 후 오류 메시지를 읽고 정류소 순위로 전환). 숫자 검증 181개 중 미확인 10개로 2문항이 템플릿 대체되었는데, 모두 근거에 있는 수(표의 문자열 셀 속 숫자, 주의 문구의 제외 개수)를 검증기가 못 읽은 경우라 검증 풀을 넓혀 재검증 시 미확인 0. 자기 점검은 7문항에서 2~3건씩 '인과 추정', '표본을 절대치로 서술', '한 달 일반화 위험' 같은 지적을 냈고, 후속 질문은 16문항 모두 LLM 제안이 채택됨. 평균 16.6초/문항, 토큰 합계 358k(문항당 약 22k; 자기 점검·후속 제안이 2회 호출 추가). 과정에서 기본 모델 ID 오타와 Messages API 미지원 파라미터(temperature)를 수정.
- **혼잡지수 타당성 검증(`docs/VALIDATION.md`, `scripts/validate_index.py`)**: "와이파이 접속자 = 방문 규모"라는 핵심 가정을 수집 주체가 다른 버스 승차(티머니 3-04)로 교차 확인했다. 관광 범주 장소 109곳(동봉 축약본 기준)에서 ① 장소의 80%가 일별로 같은 방향으로 움직이고(상관 중앙값 0.18), ② 주말/평일 쏠림 방향이 65% 일치하며, ③ 장소 간 순위 상관은 관광지·해변에서 ρ 0.3대, 전통시장·테마거리·올레코스에서는 0.2 미만(버스 승차에 통근·환승이 섞임). → 혼잡지수를 '방향·순위' 수준의 상대 지표로만 쓰고 절대 규모·도심 상권의 세밀한 순위에는 쓰지 않는다는 해석 원칙이 데이터로 뒷받침된다. **외부 기준 검증 A1(허브 공개 API「읍면동 단위 내국인 유동인구」, 통신사 기반, 2025-09 30일)**: 와이파이 장소의 80%를 40개 읍면동에 연결해 같은 날짜로 대조한 결과, 읍면동 간 순위 상관은 Spearman ρ **0.36**(log-log r 0.37)으로 와이파이가 많은 읍면동이 통신사 방문자도 많은 경향은 확인되지만, 일별 상관 중앙값은 **0.07**(양의 상관 52%)로 읍면동 전체 합계 수준에서는 날짜별 등락이 따라가지 않았고 주말 쏠림 방향 일치는 30%였다. 표본 비율(와이파이 ÷ 방문자)은 중앙값 2.3‰에 읍면동 간 0.3~25.9‰로 편차가 커서, 와이파이 기반 혼잡은 절대 규모가 아닌 순위·방향 지표로만 써야 함이 외부 데이터로도 확인된다. 통신사 '방문자수'는 도민의 주말 나들이·통학·쇼핑까지 포함해 거의 모든 읍면동에서 주말에 늘지만(1.0~1.6배), 공공 와이파이는 관광 범주 장소만 남겨도(39개 읍면동: ρ 0.25, 일별 r 0.09, 주말 일치 34%) 격차가 줄지 않았다. 즉 읍면동 단위 통신사 유동인구와 공공 와이파이 접속은 **장소 간 '어디가 많은가'는 느슨하게 공유하지만 '언제 늘고 주는가'는 서로 다른 것을 잰다**. 이에 따라 서비스는 (1) 장소 간 비교를 순위로만 말하고, (2) 날짜·요일별 변화는 그 장소 자체의 평소 평일 기준선 대비 배수(와이파이 내부 기준)로만 말하며 외부 데이터로는 뒷받침되지 않음을 한계로 명시한다. 읍면동 43개 중 다수가 도심 행정동이라 집계 단위가 너무 거칠다는 점도 한계이며, 장소 단위 외부 기준(관광지 입장객)이 확보되면 A2절로 보완한다. 관광지 입장객 CSV는 `--visitors`로 A2절이 추가된다.
- 모든 답변에 도구 인자·계산 방법·게이트 로그가 붙어 수치를 역추적할 수 있다.
- **재현 절차(운영진 코드 실행 요청 대응)**: `pip install -r requirements.txt` → `python scripts/reproduce.py --pytest`. 동봉 축약본으로 18문항을 돌려 골든 지문과 대조하고 테스트 89개를 실행한다(약 1분, API 키·인터넷 불필요). 전체 실데이터(data/raw)로는 `--data auto`.
- 한계: 와이파이=표본(상대 지표), 4-05에 시각 없음, 버스 효율=승차 수요 기준, 강우 효과·기간 비교=단순 비교(요일·공휴일·행사 미통제), 규칙 모드=정형 질문만, 자동 점검의 기본은 규칙 기반(LLM 자기 점검은 선택·추가 호출), Open-Meteo 날씨는 격자 재분석값, 로컬 7b 모델은 복합 질문 정확도가 API 모델보다 낮음. **현 제출본은 허브 공개 API 실데이터(2025-09)로 검증**되었으며, 센터 원본 적재 시 국적·방문유형·시간대 기능이 추가 활성화된다(절차: `docs/DATA_ACQUISITION.md`).
